### Qué está realmente roto

La causa raíz más importante ya quedó reducida a una sola:

```text
                 PACKET3
                    |
                    v
       sid.h:336-338  CORRECTO
                    |
                    |  transcripción equivocada
                    v
             rx550_submission.c:61
                    |
        +-----------+-----------+
        |           |           |
        v           v           v
      site 1      site 2      site 3
        |           |           |
        +-----------+-----------+
                    |
                  R1
                BLOCKER
```

La implementación actual hace conceptualmente:

```text
(OPCODE & 0xFFFF) | (COUNT << 16)
```

cuando el contrato exige:

```text
(3 << 30)
| ((OPCODE & 0xFF) << 8)
| ((COUNT & 0x3FFF) << 16)
```

Por eso:

```text
0x00020076    <- actual
0xC0027600    <- correcto
```

Ese es el único `BLOCKER` técnico principal de la reparación de PM4.

### Dirección: ya tenemos una parte muy fuerte cerrada

Hay dos caminos para el mismo `base`:

```text
                         BASE
```

Entonces:

```text

    R1 = PRESENTE

    R1 = AUSENTE

=> misma cota
=> owners distintos
=> el defecto peligroso está en el camino PGM
```

Y el límite numérico está definitivamente cerrado:

```text
RX550_IB_ADDR_MASK = 0x0000FFFFFFFFFFFF
                   = 2^48 - 1

address span = [0, 2^48)
granularidad = 4 bytes
```

No `2^46`.

### IB control word

Esto también está congelado:

```text
GFX8

31.............24  VMID / conflict aún documentado
23               VALID
22               TCL2_VOLATILE
21               PRE_ENB
20...............0 LENGTH_DW

LENGTH_DW = 21 bits
MAX       = 0x1FFFFF
MAX BYTES = 0x7FFFFC
```

Y:

```text
0x001FFFFF   -> último limpio
0x00200000   -> PRE_ENB
0x00400000   -> TCL2_VOLATILE
0x00800000   -> VALID
```

No se debe usar `0x7FFFFF` como `LENGTH_DW_MAX`.

El error está en **usar** `RX550_IB_ADDR_ALIGN=4` sobre `length_dw`, no en el valor 4.
