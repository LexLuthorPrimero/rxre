## Resumen
Implementada la Fase 2 del RXRE-007: Extensión del núcleo epistémico con módulo de seguimiento de conflictos.
Se añadió soporte explícito para registrar, consultar y resolver conflictos entre valores de registros,
distinguirlos de NOT_DETERMINED, y preservar el rastreo de auditoría completo.

## Cambios realizados

### 1. Modificación de `tools/rxre/core/store.py`
Se añadió la tabla `conflicts` al DDL existente:

```sql
CREATE TABLE IF NOT EXISTS conflicts (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    target           TEXT NOT NULL,
    offset           TEXT NOT NULL,
    conflicto_tipo   TEXT NOT NULL,
    conflicto_estado TEXT NOT NULL DEFAULT 'OPEN',
    discriminante    TEXT,
    conflicto_evidencia_json TEXT,
    creado_por       TEXT,
    creado_en        TEXT NOT NULL,
    actualizado_en   TEXT
);
```

Con índices para lookup eficiente por target, offset y estado.

### 2. Creación de `tools/rxre/core/conflicts.py`
Módulo nuevo con:

**Tipos de conflicto definidos:**
- OFFSET_COLLISION: dos valores dword_index idénticos
- SEMANTIC_CONTRADICTION: definiciones con semántica incompatible
- RESOURCE_CONFLICT: dos consumidores del mismo recurso  
- OTHER: otros tipos de conflicto

**Estados de conflicto:**
- OPEN: conflicto detectado, sin resolver
- RESOLVED: conflicto resuelto con discriminante
- DEFERRED: conflicto diferido para más investigación
- ABANDONED: conflicto descartado por no ser crítico

**API de alto nivel (auto-conexión):**
- `registrar_nuevo_conflicto(target, offset, tipo, evidencia_refs, creado_por)`
- `get_conflictos_por_target(target)`
- `get_conflictos_por_offset(target, offset_hex)`
- `actualizar_estado(conflicto_id, nuevo_estado, discriminante)`
- `resolver(conflicto_id, discriminante, evidencias_resolutivas)`
- `conflicto_abandonado(conflicto_id, motivo)`

**API de bajo nivel (requiere conexión explícita):**
- `registrar_conflicto(c, target, offset, tipo, evidencia_refs, creado_por)`
- `conflictos_para_target(c, target)`
- `conflictos_por_offset(c, target, offset)`
- `listar_conflictos(c)`
- `actualizar_estado_conflicto(c, conflicto_id, nuevo_estado, discriminante)`
- `resolver_conflicto(c, conflicto_id, discriminante, evidencias_resolutivas)`
- `conflicto_abandonado(c, conflicto_id, motivo)`

**Validaciones implementadas:**
- `tipo` debe estar en TIPOS_CONFLICTO
- `estados` deben estar en ESTADOS_CONFLICTO
- `evidencia_refs` deben referenciar results/operations/edges válidos
- Un conflicto PROVEN requiere al menos un ref válido

### 3. Registro del conflicto P0.3 existe FASE 2
El conflicto `dword_index` entre `mmCB_BLEND0_CONTROL` (0xA1E0) y `mmCB_BLEND1_CONTROL` (0xA1E1) 
ahora puede ser registrado explícitamente usando `registrar_conflicto`:

```python
registrar_conflicto(
    c, "1002:699f@c7", "0xA1E0", "OFFSET_COLLISION",
    ["res_...", "op_..."], "reg_resolve.py"
)
```

## Tabla de incompatibilidades (con NOT_DETERMINED)

| Caso | NOT_DETERMINED | CONFLICT |
|------|---------------|----------|
| Sin evidencia | Sí | No |
| Evidencia incompatible | No (sería PROVEN o REFUTED) | Sí |
| Duda epistemica | Sí | No |

Un conflicto NO implica que el valor esté PROVEN. El discriminante debe ser explícito
para pasar de OPEN a RESOLVED. Esto respeta §9: "una conclusión que no se puede
rastrear no es PROVEN".
