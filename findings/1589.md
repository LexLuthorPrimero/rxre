# FINDING 1589 — RXRE-006 P0.1: dword_index defecto distuye identidad de registros MMIO

## Defecto demostrado

```text
byte_offset // 4
```

produce:

```text
0x1AC → 0x6B
0x1AD → 0x6B
```

Esto destruye la identidad de dos registros MMIO diferentes.

### Contexto

El defecto está en la representación: cuando un consumidor toma el byte offset y lo divide entre 4 para obtener un "dword index", el resultado puede colisionar. Dos valores de byte offset distintos (diferentes en 1 byte) pueden producir el mismo índice dword al dividir entre 4.

### Localización del productor y consumidor

| Rol | Componente | Ubicación |
|---|---|---|
| **Productor** | `reg_resolve.py` — cálculo de `dword_index` | `tools/reg_resolve.py:286`: `out["dword_index"] = hex(val >> 2)` |
| **Consumidor** | `rxre_cobertura_gfx8.py` — lectura de valor | `tools/rxre_cobertura_gfx8.py:88`: `elegido.get("value", elegido.get("byte_offset"))` |

### Capa que introduce la división

El cálculo `dword_index = val >> 2` se agregó para conveniencia de presentación, sin validar si el consumidor realmente necesita el índice dword o si el byte offset debe conservarse sin transformación.

### Consumidores que requieren byte address vs dword index

- **Requiere byte address:** La mayoría de los registros MMIO se acceden mediante byte offset tal como lo declara el kernel: `@reg: dword aligned register offset`. El valor numérico es un offset en bytes y multiplicarlo por 4 da el índice dword de la capa SOC15.
- **Requiere dword index:** Algunos consumidores internos de RXRE que normalizan o agrupan registros, especialmente cuando el offset ya está alineado y el dword index es más conveniente para búsquedas.

### Colisión verificable

```text
byte_offset = 0x1AC   (= 428 en decimal)
dword_index = 0x1AC >> 2 = 0x6B (= 107 en decimal)

byte_offset = 0x1AD   (= 429 en decimal)
dword_index = 0x1AD >> 2 = 0x6B (= 107 en decimal)

0x1AC y 0x1AD son registros MMIO distintos, pero su dword index colisiona en 0x6B.
```

### Impacto

Si un consumidor depende de `dword_index` para distinguir registros, la división `byte_offset // 4` destruirá la identidad entre registros que están separados en 1 byte. Esto puede causar:

- Selección incorrecta de registros en flujos de trabajo que normalizan offsets
- Conflictos silenciosos donde dos registros distintos son tratados como el mismo
- Pérdida de corrección en la representación de offsets MMIO

### Reparación mínima

La reparación consiste en **conservar el byte offset sin transformación** y sólo derivar dword index cuando el consumidor solicite explícitamente bajo precondición de alineación:

1. El producer (`reg_resolve.py`) debe incluir ambos campos: `byte_offset` y `dword_index`, donde `dword_index` es opcional y depende de la precondición de alineación.
2. El consumer debe solicitar `dword_index` explícitamente; no debe asumir que `byte_offset >> 2` es suficiente.
3. Añadir un `warning` o `note` en la salida que explique la relación y el riesgo de colisión.

### Criterio de terminación

PASS únicamente si queda demostrado:

1. **donde debe conservarse el byte offset** — el valor numérico es un offset en bytes, tal como declara el kernel en `@reg: dword aligned register offset`.
2. **donde, si corresponde, puede derivarse un dword index** — bajo precondición explícita de alineación (offset módulo 4 == 0), y únicamente cuando el consumidor lo solicite.
3. **colisión documentada** — el hecho de que `byte_offset // 4` puede producir valores colisionados está documentado y advertido.
4. **representation no pierde identidad** — el byte offset siempre está disponible en la salida; dword index es derivado y opcional.
